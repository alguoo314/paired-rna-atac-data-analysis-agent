- `tests/test_core_analyses.py`: 11 tests (real data, `n_cells=3000`, module-scoped fixture so the ~4-minute snapatac2 step runs once for the whole file) — QC columns in sane ranges, both modalities produce >1 Leiden cluster, ARI in valid range, contingency table shape/sum correct, and all 5 canonical PBMC markers (CD14, LYZ, MS4A1, CD3E, NKG7) recovered as significant markers. Full suite (all steps): 15 (steps 1-2) + 11 (step 3a) = 26 passed.

**Actual numbers observed (n_cells=3000, seed=0):** 14 RNA Leiden clusters, 16 ATAC Leiden clusters, ARI = 0.517 (moderate agreement — expected, not optimized for). All 5 canonical markers recovered. Median FRiP ≈ reasonable range, TSS enrichment and nucleosome signal both well within normal PBMC ranges (see code docstrings/logs for exact medians on a given run — not hardcoded here since they'll shift slightly with subsample seed/size).

**Design decisions:**
- **TSS enrichment vs. nucleosome signal use two different tools deliberately.** snapatac2 is CLAUDE.md's named tool for ATAC QC and has a proper per-cell `tsse` metric with a bundled gene-annotation download (no full genome sequence needed) — used for TSS enrichment. But snapatac2's only nucleosome-related output (`frag_size_distr`) is dataset-level, and its `recipe_10x_metrics` per-cell nucleosome fractions need a raw BAM file we don't have. `muon.atac.tl.nucleosome_signal` (already in the approved stack) provides the real per-cell metric directly from the fragments file, so it's used instead — a documented, defensible substitution, not a silent shortcut.
- **Runtime cost accepted, not optimized away:** `snapatac2.pp.import_fragments` sorts the entire ~2GB fragments file every call regardless of subsample size (~4 min fixed cost). This is fine for a once-per-dataset fixed-core pass; if this becomes a bottleneck for the eval harness (Day 2, many repeated runs), caching the sorted/whitelisted intermediate would be the fix — not done now since it's premature.
- **Marker recovery test uses padj+logFC thresholds, not top-N rank.** Initially tried literal "in top 25 marker genes by rank" and it failed for CD14/CD3E even though both were genuine, highly significant markers of the correct cluster (Wilcoxon raw score ranked other genes higher; T cells split across 4 of the 14 Leiden clusters diluted per-cluster significance ranking). Switched to the standard Seurat/Scanpy "is this a marker" criterion (`pvals_adj < 0.05` and `logfoldchanges > 1` in at least one cluster), which all 5 canonical markers pass and which is more robust to Leiden-resolution-dependent cluster splitting.
- **Dropping ATAC LSI component 0 needed an explicit array slice, not `n_pcs`.** `scanpy.pp.neighbors(use_rep=..., n_pcs=N)` takes the *first* N columns of the representation, not "all but the first" — so `n_pcs=ndim-1` would have kept the depth-correlated component and dropped the last one instead (the opposite of the intended standard scATAC practice of excluding component 0). Fixed by explicitly building `X_lsi_no_depth = X_lsi[:, 1:]` and using that as `use_rep` with no `n_pcs`.
- Peak/gene filtering (`sc.pp.filter_genes(min_cells=3)`) added before TF-IDF/normalization on both modalities — without it, zero-count peaks in the 3000-cell subsample caused divide-by-zero in muon's IDF computation.

**Uncertain / deferred:** Gene activity scores and chromVAR-style motif deviations are step 3b (separate fork) — not built here. `hg38.2bit` still untouched, reserved for step 3b's motif work.

Per-tool try/except means one bad tool call (bad gene name, network hiccup) returns an `is_error` tool result instead of crashing the whole run; only the top-level API call itself uses a specific `RateLimitError`/`APIStatusError`/`APIConnectionError` chain. `ReasoningTrail` writes a human-readable markdown log per run to `logs/agent_runs/<timestamp>.md` (gitignored) — model, question, each turn's text + tool calls + result summaries, final answer, turn count, cost.

**Scope limitation (named, not hidden):** CLAUDE.md's fault list also includes cell-line/cell-type label swaps and mixed samples — both need multi-sample/multi-cell-line structure this single-sample PBMC dev dataset doesn't have (that's the multi-cell-line showcase data, a later stretch goal, not built). Only the three fault types below are implemented.

**Real measured numbers:**
- **Shuffled RNA-ATAC pairing** (fractions 0.2/0.5/1.0, cheap — reuses the clean fixed-core result, only cross-modal signals recomputed): ARI 0.467 (clean) → 0.287 → 0.140 → 0.0004; SPI1 TF-motif ρ 0.595 (clean) → 0.442 → 0.351 → 0.036. Clean monotonic degradation toward chance-level agreement at 100% shuffle — exactly CLAUDE.md's point that this fault "looks fine per modality, breaks joint structure": each modality's own QC/clustering/gene-activity/motif-deviation numbers are provably unchanged (verified: `(shuffled["atac"].X != mdata["atac"].X).nnz == 0` at fraction=0.0, and per-cell values travel with their true source cell at any fraction), only the *cross-modal* signals move.
- **Injected doublets** (rates 0.05/0.1/0.2): `doublet_score` (continuous) is correctly and consistently elevated in synthetic cells at all three rates. `predicted_doublet` (scrublet's automatic binary threshold) becomes unstable at rate=0.2 — both the real-cell and synthetic-cell predicted rates collapse toward 0 instead of showing the expected separation seen at 0.05/0.1. This is scrublet's own threshold-detection heuristic breaking down when the actual doublet fraction is unusually high and doesn't match its internal bimodality assumption — a genuine limitation of the QC tool, not a bug in the injector. **Implication for later eval scoring: score doublet detectability primarily on the continuous `doublet_score`, not the binary `predicted_doublet` flag**, especially at higher severities.
- **ATAC downsampling** (keep_frac=0.2, the one `@pytest.mark.slow` real-rerun case): `n_fragment` median 13305 → 2656.5 (−80.0%), `tss_enrichment` median 16.69 → 14.48 (−13.2%), `nucleosome_signal` median 0.906 → 0.925 (+2.1%, i.e. essentially unchanged). The first two are absolute-depth-sensitive metrics and drop as expected under downsampling; `nucleosome_signal` is a length-ratio (mono-nucleosomal / nucleosome-free fragments) and fragments are dropped *uniformly at random regardless of length*, so there's no mechanism that should shift that particular ratio — its near-zero change is the expected, correct result, not a failure to detect the fault. Not every fixed-core metric should be expected to react to every fault type; this is documented in the test as a sanity check (finite, non-negative), not a directional assertion, specifically because I initially wrote an unjustified directional claim ("heavier downsampling should lower the ratio") and caught it as wrong before committing — length-unbiased sampling doesn't predict that.

**Design decisions:**
- **Shuffled-pairing reuse optimization works and is real**, not just claimed: verified `mdata["atac"].obs_names` is unchanged by the shuffle (only which row sits under which label changes), so the already-computed clean fixed-core result's per-cell fields are valid as-is for the shuffled case; only `rna_atac_cluster_agreement` and `tf_expression_motif_correlation` get recomputed. Saves a ~17-minute snapatac2 rerun per severity level.
- **Downsampling is genuine fragment-line dropping**, not just peak-matrix thinning — `_stream_downsample_fragments` streams the real ~2GB fragments file and independently drops lines at `1 - keep_frac` probability, then bgzip+tabix-indexes the result, so the fault propagates consistently into every fragments-derived metric (TSS enrichment, nucleosome signal, gene activity if ever scored) rather than only affecting the peak count matrix.
- **Doublets are real count summation of random real-cell pairs**, both modalities together (matching what a real physical doublet is: one droplet, two nuclei, contributing to both readouts), with fragments-derived ATAC fields explicitly left `NaN` for synthetic cells (they have no entry in the real fragments file) rather than faked or silently zeroed.
- **A real bug already caught and documented by the fork that did most of this build** (see `downsample_atac_fragments`'s docstring): `pysam.tabix_index`-ing the downsampled file is required, not optional — `muon.atac.tl.locate_fragments` silently swallows a missing/wrong index (broad `except Exception: print(...)`, no raised error) and would leave a stale fragments path in `.uns`, producing numbers that look valid but are actually computed on the wrong file.
- **A real bug I found and fixed after the fork handed off** (`score_downsampling` crashing with an uncaught `StopIteration`): traced to `muon.atac.tl.nucleosome_signal` doing one genome-wide `fragments.fetch()` capped at a fixed `n = n_obs * 1e4` total reads, not per-barcode iteration — its `except KeyError: pass` only swallows unknown-barcode lines, not the `StopIteration` that `next()` raises once the file is exhausted. A downsampled file easily has fewer total lines than that fixed target. My first attempted fix (filtering out zero-fragment barcodes) was based on a wrong diagnosis and didn't actually resolve the crash — found the real cause by reading muon's source directly rather than guessing a second time. Fixed by capping `n` at the real total fragment count (already known from the snapatac2 import a few lines earlier, no extra cost).
- **Eval subsample size:** reused Day 1's `n_cells=500` agent fixed-core cache as the shared clean baseline across all three fault types, rather than a separate eval-specific size — large enough for meaningful clustering/doublet signal, and reusing the already-warm disk cache avoids paying the ~17-minute fixed cost a fourth time.

**A real bug found and fixed in the grounding checker while validating it against real (not just constructed) output:** the initial implementation matched only ASCII scientific notation (`3.5e-49`); real Haiku answers commonly write `3.5 × 10⁻⁴⁹` (Unicode), which the plain regex decomposed into a lone `3.5` fragment that then failed to match against the tool's actual `3.53e-49` — a false-positive "ungrounded" flag on a citation that was actually correct. Fixed by matching the whole Unicode-notation span as one number first, and switched the match criterion from decimal-place-exact rounding to relative-tolerance comparison (handles both notations uniformly, and is more robust than trying to define "decimal places" for a citation like "2 × 10⁻⁵"). Verified the fix by regenerating the real report end-to-end and confirming the previously-flagged, actually-correct citations now pass.

**Design decisions:**
- **Motif significance test is Mann-Whitney U (one-sided, "greater"),** not a t-test — chromVAR deviation z-scores aren't guaranteed normal, and the directional hypothesis (motif MORE accessible in the labeled cluster) is exactly what a one-sided rank test expresses, not just "different."
- **Cluster annotation requires a UNIQUE cell-type match, not just "any."** An early version risked labeling a cluster ambiguously if multiple checklist markers happened to be significant in it; requiring exactly one distinct cell_type keeps the motif-scoring step honest — testing a motif against a cluster whose identity is itself ambiguous would be circular evidence.
- **The grounding checker only checks internal consistency (traces to this run's real tool output), not external PMID validity** — a PMID returned by a real `search_pubmed` call is real by construction (E-utilities wouldn't return a fake one), so a second external verification pass would be redundant; the risk this checker is built to catch is the model inventing a citation, not E-utilities being wrong.
- **Report writer reused the real, already-warm `agent_fixed_core_cache` (n=500)** rather than a separate report-specific run — same dataset the checklist scorer and step-4 agent loop already validated against, no new computation needed.

- **This is a deliberate, bounded exception to the MVP's "agent does not write new analysis code" rule**, scoped narrowly: only pre-aggregated statistics ever enter the executed code's namespace, never raw per-cell data, and it's opt-in per investigation (a separate tool list), not silently available to every agent run.

## Stretch — Correction: motif deviations for the private data ARE buildable

The project owner caught this directly in conversation and asked for it to actually be built rather than left deferred. It is now built.

**What changed:**
- `data/private_loader.py`: now parses peak coordinates into `atac.var["chrom"/"start"/"end"]` at load time (reuses the public loader's `_parse_peak_coords`, not a reimplementation) — the one missing piece, not a large undertaking.
- `core/private_pipeline.py`: new `_sanity_check_peak_sequences` (extracts real sequence for a sample of peaks from `hg38.2bit` via the same code path the real computation uses, and hard-fails if it looks degenerate — mostly-N bases or implausible GC content — rather than silently trusting an unverified genome-build match) and `compute_private_motif_deviations` (runs the sanity check, then calls the PUBLIC pipeline's `compute_motif_deviations` completely unmodified — it already only needs `.var["chrom"/"start"/"end"]` and `hg38.2bit`/JASPAR, both dataset-agnostic, so no adapter was needed). Wired into `run_private_fixed_core` by default, same as the public pipeline.
- **A real, separate bug found and fixed while building this** (not the genome-build question — that passed cleanly): `pychromvar`'s `compute_deviations` divides `adata.X` in place, which numpy rejects when `X` is an unsigned-integer dtype (this private dataset's raw ATAC counts are `uint`; the public PBMC loader's `.X` happens to already be `float32` from a different code path, which is why this never surfaced before).
